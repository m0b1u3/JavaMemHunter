# JavaMemHunter 开发进度分析（2026-05-28）

## 1. 当前阶段结论

项目已进入 **v0.7 功能完成 + 稳定性收敛** 阶段，不再是早期 PoC：

- 核心链路已覆盖：`scan -> clean --dry-run -> clean --confirm -> verify`。
- 清理对象从 v0.6 的 Filter 扩展到 v0.7 的 Servlet / Listener / Valve。
- 清理过程具备审计闸门（plan stale / forced 三方一致）与失败回滚。
- 最近提交以 `fix/docs/test` 收敛为主，说明主功能已落地，正在做可用性与可维护性打磨。

## 2. 已完成能力版图（按演进）

1. **检测能力已从类扫描扩展到容器运行时与 Spring 运行时（v0.2）**。
2. **风险判断体系成熟（v0.3）**：规则引擎 + 白名单 + explain 证据化输出。
3. **攻击行为识别更深入（v0.4）**：ASM 字节码调用级匹配，覆盖 Runtime.exec / ProcessBuilder / 反射滥用等关键手法。
4. **具备“基线对比”运维能力（v0.5）**：可识别启动后新增对象，适配持续巡检场景。
5. **进入“可治理”阶段（v0.6~v0.7）**：不仅能报，还能可控清理（dry-run + confirm + verify + evidence + rollback）。

## 3. 代码与提交流水信号（客观进度）

从最近提交看：

- 已合入 `feature/v0.7-tomcat-cleaners-extension`，说明 v0.7 主干功能集成完成。
- 紧随其后出现 `schema migration`、`final review nit`、`README/design doc`、`dispatch test` 等提交，符合“功能完成后收口”的典型节奏。
- 仓库规模约 167 个文件，已具备工程化分层，不是一次性脚本型项目。

## 4. 测试与验证成熟度评估

- README 明确标注 v0.7 有 **197 tests**，并指出完整 E2E 需手工拉起 test-target + 注入 4 类假马。
- 这意味着：
  - **单元/模块级验证较充分**（尤其 cleaner phase 流程与分发路径）。
  - **真实环境回归仍偏手工**，自动化 E2E/CI 编排还有提升空间。

## 5. 风险与短板（当前不是“做不到”，而是“离生产最佳实践还有距离”）

1. **E2E 依赖手工流程**：证据归档虽规范，但回归成本较高。
2. **版本兼容迁移成本**：v0.7 对旧 evidence schema 不兼容，运维需重跑 dry-run。
3. **生产落地策略仍保守**：README 仍建议维护窗口重启，说明运行时清理后的一致性风险尚未完全工程化消除。

## 6. 综合判断（进度百分比）

若以“可交付的内存马检测+治理工具”为目标，可粗略评估：

- **功能完成度：85%~90%**（扫描、评分、基线、清理、验证、证据链均已具备）。
- **工程化完成度：75%~85%**（模块化和测试基础较好，但自动化 E2E/CI 与运维迁移体验可继续加强）。
- **生产可运维度：70%~80%**（有审计与回滚，但仍需要重启建议和人工确认流程兜底）。

## 7. 下一阶段建议（优先级）

- P0：补齐自动化 E2E（最少覆盖 Filter/Servlet/Listener/Valve 四类注入-清理-验证闭环）。
- P1：把 evidence schema 版本化并提供迁移器/兼容读取策略，降低升级摩擦。
- P1：输出“生产操作手册”模板（变更窗口、回滚预案、验收指标、审计留存）。
- P2：补充更多容器/框架版本矩阵与异常 case（并发请求中清理、destroy 抛错路径）。
