## 1. 目标与范围

### 1.1 目标

把清理能力从 Tomcat 4 类扩展到 Spring MVC 两类（Mapping / Interceptor），沿用 v0.6 的 5-Phase 模板（A 复扫 / B 备份 / C 清理 / D 销毁 / E verify）+ v0.6.1 审计闸门（PlanReconciler + EXIT_PLAN_STALE + Phase D 三标签），并把 v0.7 `AbstractTomcatCleaner` 中与容器无关的逻辑上提到通用 `AbstractCleaner`，新增 `AbstractSpringCleaner`。

**2 类新 Cleaner：**

1. **SpringMappingCleaner** — 清理 `spring-mapping`。Phase C 调官方 `AbstractHandlerMethodMapping.unregisterMapping(RequestMappingInfo)`；rollback 用 `registerMapping(info, handler, method)` 重新注册。
2. **SpringInterceptorCleaner** — 清理 `spring-interceptor`。Phase C 反射改 `adaptedInterceptors` List（原子副本替换，与 v0.7 Listener 同款）；rollback 恢复原 List。

**架构层目标：**

3. **AbstractCleaner**（新基类）：从 `AbstractTomcatCleaner` 上提 `plan()` / `execute()` 模板 + Phase D 三标签 `releaseTargetByConvention` + Phase E rollback 决策。完全与容器无关。
4. **AbstractTomcatCleaner**：改为 `extends AbstractCleaner`，只保留 Tomcat-specific 的内容（`standardContext` 字段 + `contextPathOf` 实现）。
5. **AbstractSpringCleaner**：`extends AbstractCleaner`，持有 `applicationContext`，提供 Spring 共享 helper（`loadClass`、`getBeansOfType`）。
6. **CleanerRegistry**：`resolve(type, tomcatCtx, springCtx)` 三参 + 注册时声明 `ContextKind.{TOMCAT,SPRING}`。
7. **MemHunterAgent.findFindingById**：扩展为先定位 ApplicationContext（复用 `SpringScanner` 定位逻辑），然后跑 4 Tomcat + 2 Spring scanner 合并。dispatch 把 tomcatCtx + springCtx 都传给 `registry.resolve`。
8. **CleanExecutionException 加 `didMutate` 标志**：顺手修 v0.7 final review nit #3，让 Phase B 前置失败时 `rolledBack=false` 准确反映"未动运行时"。

### 1.2 非目标

- **不**做 Spring Bean 清理（v0.9+）。
- **不**改 scanner（SpringMappingScanner / SpringInterceptorScanner 保持只读，cleaner 自行重定位活对象）。
- **不**改 evidence 目录布局 / CleanPlan schema（v0.7 的 `targetName/targetClass/details` 已足够通用）。
- **不**改 PlanReconciler 比对逻辑（targetClass/score/forced 对 Spring finding 同样适用）。
- **不**提供 batch clean。

## 2. 组件改动

### 2.1 新增

#### 2.1.1 AbstractCleaner（容器无关模板基类）

`agent/.../cleaner/AbstractCleaner.java`：

```java
public abstract class AbstractCleaner implements Cleaner {
    protected RollbackStrategy rollback;
    protected String currentTargetName;
    protected String currentTargetClass;
    protected Finding currentFinding;

    // 子类实现
    protected abstract boolean supportsType(String type);
    protected abstract Finding locateOnRescan(String findingId);
    protected abstract Map<String,Object> buildDetails(Finding finding);
    protected abstract void doPhaseB(Finding finding);
    protected abstract void doPhaseC() throws CleanExecutionException;
    protected abstract List<String> phaseDLabels();
    protected abstract boolean stillPresentOnRescan(String findingId);
    protected abstract List<String> phaseSteps();
    protected abstract String contextPathOf(Finding finding);

    // final: plan() / execute() / releaseTargetByConvention() / phaseDThrew()
}
```

把 v0.7 `AbstractTomcatCleaner` 里**所有**与 Tomcat 字段无关的逻辑原样上提。唯一新增的抽象方法是 `contextPathOf(finding)`（原 plan() 内联读 `attributes.get("contextPath")`，Spring 没有 contextPath，抽出来让子类决定）。

`execute()` 的 Phase C catch 块改进（配合 §2.2.4 didMutate）：

```java
} catch (CleanExecutionException ce) {
    result.success = false;
    result.rolledBack = ce.didMutate();   // 未动运行时 → false
    result.failureReason = "Phase C failed: " + ce.getMessage();
    result.executedSteps.add(ce.didMutate()
        ? "phase-C: FAILED, rolled back"
        : "phase-C: FAILED before mutation");
    return result;
}
```

#### 2.1.2 AbstractSpringCleaner

`agent/.../cleaner/AbstractSpringCleaner.java`：

```java
public abstract class AbstractSpringCleaner extends AbstractCleaner {
    protected final Object applicationContext;

    protected AbstractSpringCleaner(Object applicationContext) {
        this.applicationContext = applicationContext;
    }

    @Override protected String contextPathOf(Finding f) { return ""; }

    protected Class<?> loadClass(String name) {
        try {
            return Class.forName(name, false, applicationContext.getClass().getClassLoader());
        } catch (Throwable t) { return null; }
    }

    @SuppressWarnings("unchecked")
    protected Map<String,?> getBeansOfType(Class<?> type) {
        try {
            java.lang.reflect.Method m =
                applicationContext.getClass().getMethod("getBeansOfType", Class.class);
            return (Map<String,?>) m.invoke(applicationContext, type);
        } catch (Throwable t) { return null; }
    }
}
```

### 2.2 修改

#### 2.2.1 AbstractTomcatCleaner

- 改为 `extends AbstractCleaner`
- 删除已上提到基类的 `plan()` / `execute()` / `releaseTargetByConvention()` / `phaseDThrew()`
- 实现 `contextPathOf(finding)` → `String.valueOf(finding.attributes.getOrDefault("contextPath",""))`
- 保留 `standardContext` 字段 + 构造器
- 4 个 Tomcat cleaner 子类**不受影响**（它们 extends AbstractTomcatCleaner，方法签名没变）

#### 2.2.2 CleanerRegistry

- `register(typeOrPrefix, boolean prefix, ContextKind kind, factory)` —— 四参
- `resolve(type, tomcatCtx, springCtx)` —— 三参，按 ContextKind 选 context；目标 context 为 null 时返回 null
- `defaultRegistry()` 注册 6 个 cleaner：

```java
public static CleanerRegistry defaultRegistry() {
    return new CleanerRegistry()
        .register("tomcat-filter",      false, ContextKind.TOMCAT, TomcatFilterCleaner::new)
        .register("tomcat-servlet",     false, ContextKind.TOMCAT, TomcatServletCleaner::new)
        .register("tomcat-listener-",   true,  ContextKind.TOMCAT, TomcatListenerCleaner::new)
        .register("tomcat-valve",       false, ContextKind.TOMCAT, TomcatValveCleaner::new)
        .register("spring-mapping",     false, ContextKind.SPRING, SpringMappingCleaner::new)
        .register("spring-interceptor", false, ContextKind.SPRING, SpringInterceptorCleaner::new);
}
```

内部用 `Registration { boolean prefix; ContextKind kind; Function<Object,Cleaner> factory; }` 值对象存储；`resolve`：

```java
public Cleaner resolve(String type, Object tomcatCtx, Object springCtx) {
    if (type == null) return null;
    Registration r = byEquals.get(type);
    if (r == null) {
        for (Map.Entry<String, Registration> e : byPrefix.entrySet()) {
            if (type.startsWith(e.getKey())) { r = e.getValue(); break; }
        }
    }
    if (r == null) return null;
    Object ctx = (r.kind == ContextKind.SPRING) ? springCtx : tomcatCtx;
    if (ctx == null) return null;
    return r.factory.apply(ctx);
}
```

#### 2.2.3 MemHunterAgent

- `findFindingById(tomcatCtx, springCtx, id)` —— 跑 4 Tomcat + 2 Spring scanner（springCtx 非 null 时）
- 新增 `locateApplicationContext(...)` —— 复用 SpringScanner 暴露的定位方法
- dispatch（dry-run + confirm）：先定位 springCtx，调 `registry.resolve(finding.type, tomcatCtx, springCtx)`；resolve 返回 null 时写友好 CleanResult + `EXIT_EXECUTE_FAILED`

#### 2.2.4 CleanExecutionException + didMutate

```java
public class CleanExecutionException extends RuntimeException {
    private final boolean didMutate;
    public CleanExecutionException(String msg, boolean didMutate) {
        super(msg); this.didMutate = didMutate;
    }
    public CleanExecutionException(String msg, Throwable cause, boolean didMutate) {
        super(msg, cause); this.didMutate = didMutate;
    }
    public boolean didMutate() { return didMutate; }
}
```

v0.7 既有 cleaner 的 `throw new CleanExecutionException("Phase C forward step failed", t)` 改为 `(..., t, true)`（Phase C forward 失败时已动运行时并回滚）。Phase B 前置失败抛 `(..., false)`。

#### 2.2.5 SpringScanner 暴露定位

给 `SpringScanner` 加 public `locateContexts(tomcatContexts, servletInstances, report)` 返回定位到的 ApplicationContext 列表（不扫描），供 MemHunterAgent dispatch 复用。

## 3. 数据流

### 3.1 多 context dispatch 路径（confirm 阶段）

```text
用户：clean --id <fid> --confirm [--force]
         │
         ▼
MemHunterAgent.dispatchCleanConfirm(inst, args):
  ┌──────────────────────────────────────────────────────────────┐
  │ 1. tomcatCtx = tomcat.locateContexts(inst).get(0)             │
  │ 2. springCtx = locateApplicationContext(tomcatCtx, inst)      │
  │    └─ 可能为 null（非 Spring 应用）                            │
  │ 3. persisted = CleanPlanReader.read(planFile)                 │
  │ 4. finding = findFindingById(tomcatCtx, springCtx, id)        │
  │    ├─ 4 Tomcat scanner (tomcatCtx)                            │
  │    ├─ 2 Spring scanner (springCtx, 若非 null)                 │
  │    ├─ RuleEngine.evaluate(合并结果)                            │
  │    └─ 按 id 匹配                                               │
  │ 5. cleaner = registry.resolve(finding.type, tomcatCtx, springCtx) │
  │    ├─ TOMCAT → factory.apply(tomcatCtx)                       │
  │    ├─ SPRING → factory.apply(springCtx)                       │
  │    │   └─ springCtx==null → null → 友好失败                   │
  │    └─ 未注册 → null → EXIT_EXECUTE_FAILED                     │
  │ 6. fresh = cleaner.plan(finding, confirmForceFlag)           │
  │ 7. PlanReconciler.requireConsistent(persisted, fresh, flag)  │
  │    └─ stale → EXIT_PLAN_STALE                                 │
  │ 8. result = cleaner.execute(fresh, confirmForceFlag)         │
  │ 9. EvidenceWriter.writeResult(id, result)                   │
  └──────────────────────────────────────────────────────────────┘
```

步骤 2 + 5 的 ContextKind 分流是 v0.8 唯一的新 dispatch 逻辑，其余沿用 v0.6.1/v0.7。

### 3.2 SpringMappingCleaner 的 Phase B/C/D/E

```text
Phase A (基类)：locateOnRescan(id) 跑 SpringMappingScanner 找 finding + score≥7 闸门

Phase B (备份)：
  1. getBeansOfType(AbstractHandlerMethodMapping) 拿所有 mapping bean
  2. 对每个 bean 调 getHandlerMethods() → Map<RequestMappingInfo, HandlerMethod>
  3. 对每个 entry：
     若 String.valueOf(info) == finding.details["pattern"]（infoString）
     且 handlerMethod.getBeanType().getName() == finding.targetClass
     → 命中：备份 mappingBean / info / handlerMethod
  4. rollback = MappingRollbackStrategy(mappingBean, info, handlerMethod)
     若未命中 → backup=null（Phase C 前检测，抛 CleanExecutionException(false)）

Phase C (清理)：
  mappingBean.unregisterMapping(info)   ← 官方 API，反射调用
  （内部清 mappingLookup + pathLookup + registry）

Phase D：phaseDLabels() → ["phase-D: no-release-method"]（仅注销路由，bean 留存）

Phase E (验证)：
  stillPresentOnRescan(id) 再跑 SpringMappingScanner
  仍命中 → rollback.restore() = mappingBean.registerMapping(info, handler, method)
```

**infoString 重定位健壮性**：`RequestMappingInfo.toString()` 在同一 JVM 内对同一路由稳定（`{GET [/path]}`）。Phase B 每次在当前进程重新遍历 live mapping，跨进程（dry-run→confirm 两次 attach）也 OK。

### 3.3 SpringInterceptorCleaner 的 Phase B/C/D/E

```text
Phase A (基类)：locateOnRescan(id) 跑 SpringInterceptorScanner

Phase B (备份)：
  1. getBeansOfType(AbstractHandlerMapping) 拿所有 mapping bean
  2. 对每个 bean 反射读 adaptedInterceptors (List)
  3. 找到 className == finding.targetClass 的 interceptor
  4. 备份：受影响的 (mappingBean, 原 adaptedInterceptors List 副本) 列表
     —— 一个 interceptor 可能注册到多个 mapping bean，全部备份
  5. rollback = InterceptorRollbackStrategy(备份列表)

Phase C (清理)：原子副本替换（每个受影响 mapping bean）
  newList = new ArrayList<>(adaptedInterceptors)
  newList.removeIf(i -> i.getClass().getName().equals(targetClass))
  反射 setField(mappingBean, "adaptedInterceptors", newList)

Phase D：phaseDLabels() → ["phase-D: no-release-method"]（POJO）

Phase E (验证)：
  stillPresentOnRescan(id) 再跑 scanner
  仍命中 → rollback.restore() 把每个备份的原 List 反射写回
```

### 3.4 Phase D 标签

| Cleaner | 销毁 | 标签 |
|---|---|---|
| SpringMapping | 无（仅注销路由，bean 留存） | `phase-D: no-release-method` |
| SpringInterceptor | 无（POJO） | `phase-D: no-release-method` |

两类 Spring cleaner Phase D 都 no-release（与 v0.7 Listener 一致）。Bean 销毁是 v0.9。

### 3.5 ApplicationContext 定位复用

`SpringScanner.locate(...)` 当前 private。v0.8 给 SpringScanner 加 public `locateContexts(tomcatContexts, servletInstances, report)`，返回定位结果（不扫描）。MemHunterAgent dispatch 调它拿 springCtx；既有 `scan(...)` 内部也改调它（消除重复）。

## 4. 错误处理

### 4.1 springCtx 为 null

`resolve` 提前拦截：目标 context（SPRING→springCtx）为 null → 返回 null。dispatch 写友好 CleanResult `"no cleaner available for type: spring-mapping (ApplicationContext not located)"` + `EXIT_EXECUTE_FAILED`。避免把 null 传进 factory 产生半初始化 cleaner。

### 4.2 Phase B 重定位失败

- Mapping：getHandlerMethods() 找不到匹配 infoString+targetClass → backup=null → Phase C 前检测 → `throw new CleanExecutionException("mapping not located during Phase B", false)`
- Interceptor：所有 mapping bean 都找不到 className 匹配 → 同上

`didMutate=false`，execute() 据此设 `rolledBack=false`（未动运行时）。

### 4.3 Phase C 失败 + Rollback 分层

| Cleaner | Rollback |
|---|---|
| SpringMapping | `mappingBean.registerMapping(info, handler, method)` 重新注册 |
| SpringInterceptor | 备份的原 adaptedInterceptors List 反射写回所有受影响 mapping bean |

catch 链：
- `CleanExecutionException(didMutate=true)` → `success=false, rolledBack=true`
- `CleanExecutionException(didMutate=false)` → `success=false, rolledBack=false`
- `RollbackFailedException` → `success=false, rolledBack=false, failureReason="ROLLBACK FAILED: ..."`

### 4.4 unregisterMapping / registerMapping 反射失败

- `unregisterMapping(RequestMappingInfo)` Spring 4.0+ public；版本不符 → NoSuchMethodException → Phase C 抛 CleanExecutionException(didMutate=false) → rollback no-op → 提示重启
- `registerMapping(info, handler, Method)` 用于 rollback；rollback 时不可用 → `RollbackFailedException` → 提示重启（危险路径：mapping 已注销但恢复不了）

### 4.5 Phase D / Phase E

- Phase D 两类都 no-release，无异常路径
- Phase E 验证失败 → 自动 rollback（基类逻辑）

### 4.6 didMutate 修复惠及 v0.7

`CleanExecutionException` 加 didMutate 后，v0.7 的 4 个 Tomcat cleaner 的 Phase C catch 也改 `(..., t, true)`，同时修掉 v0.7 final review nit #3（Valve target==null 时 rolledBack 误报 true）。

## 8. 风险与限制

| 风险 | 缓解 |
|---|---|
| AbstractTomcatCleaner 上提逻辑引入 v0.7 回归 | Task 2 先跑 4 Tomcat cleaner 既有测试再重构；TDD 保证绿 |
| RequestMappingInfo.toString() 跨 Spring 版本格式差异 | Phase B 在同进程重定位，只要 scanner 和 cleaner 用同一 toString 即对称；不依赖跨版本稳定 |
| unregisterMapping 签名跨 Spring 版本差异 | Spring 4.0+ 一致；反射失败友好提示重启 |
| 一个 interceptor 注册到多个 mapping bean | Phase B/C/rollback 遍历所有受影响 bean（与 v0.7 Listener 双数组同理） |
| registerMapping rollback 失败（mapping 已注销恢复不了） | RollbackFailedException → 明确提示重启服务 |
| springCtx 定位失败（非标准 Spring Boot） | resolve 返回 null + 友好 CleanResult；不抛 NPE |
| handler bean 仍在 BeanFactory（路由注销但 bean 留存） | v0.8 范围只注销路由；Bean 清理 v0.9 明示 |

## 9. 兼容性策略

| 维度 | 策略 |
|---|---|
| Spring 4.x / 5.x / 6.x | unregisterMapping/registerMapping/adaptedInterceptors 在这些版本一致；反射不依赖编译期 Spring |
| Spring Boot 2 / 3 | ApplicationContext 定位复用 v0.5 既有 provider（DispatcherServletProvider / ServletContextAttrProvider） |
| 非 Spring 应用 | springCtx=null，Spring cleaner 不可用但 Tomcat cleaner 正常 |
| v0.7 evidence 文件 | CleanPlan schema 不变，v0.7/v0.8 evidence 互通（PlanReconciler 仍按 targetClass/score/forced 比对） |
