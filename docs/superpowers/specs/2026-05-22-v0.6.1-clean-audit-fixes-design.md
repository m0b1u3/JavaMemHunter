## 1. 目标与非目标

### 1.1 目标

修补 v0.6 Final Review 提出的 3 个 Important 审计链问题，闭环 v0.6 的生产安全门：

1. **Plan staleness 校验**：`clean --confirm` 阶段强制比对持久化 `clean-plan.json` 与新生成 plan 的 `findingId / filterClass / score / forced`。任一不同 → 拒绝、退出非零、写 `CleanResult{success=false, failureReason="plan stale: ..."}`。
2. **Forced 字段一致性**：`clean --confirm` 阶段的 `--force` 标志必须与持久化 plan.forced 严格相等。dry-run 不带 force → confirm 不能补 force；反之亦然。
3. **Phase D 步骤标签精细化**：`executedSteps` 区分 3 个 Phase D 状态：
   - `phase-D: destroy-ran` —— `release()` 成功调用
   - `phase-D: no-release-method` —— FilterConfig 类没有 `release` 方法
   - `phase-D: destroy-threw: <Class>: <message>` —— `release()` 抛异常（仍容忍）

### 1.2 非目标

- **不**改动 Phase C 算法（已稳定）。
- **不**引入新 CLI 选项。
- **不**改 evidence 目录布局。
- **不**补 v0.6 Review 提到的 Phase C 并发 ThreadLocal/CountDownLatch 测试（review 自身标注为非必须）。
- **不**处理 v0.6 Final Review 的 4 个 Nits（异常类名记录、ReflectFailedException 类型化、AgentArgs 严格未知 option、RollbackManager step 上下文）—— 后续版本处理。

## 2. 组件改动

### 2.1 新增

#### 2.1.1 `agent/src/main/java/com/memhunter/agent/cleaner/PlanReconciler.java`

静态工具类，单一职责：比对持久化 plan 与新生成 plan + confirm-time force 标志，发现不一致即抛 `PlanStaleException`。

```java
public final class PlanReconciler {
    private PlanReconciler() {}

    /**
     * @throws PlanStaleException 任一字段不一致即抛出，fail-fast 在首个差异。
     *   字段检查顺序：findingId → filterClass → score → forced。
     *   forced 校验三方等价：persisted.forced ≡ fresh.forced ≡ confirmForceFlag。
     */
    public static void requireConsistent(
            CleanPlan persisted, CleanPlan fresh, boolean confirmForceFlag);
}
```

**比对字段（任一不同即 stale）：**
- `findingId`
- `filterClass`
- `score`
- `forced`（且必须 == confirmForceFlag）

**不比对：** `generatedAt`、`evidenceDir`、`planFile`、`steps`、`level`、`urlPatterns`、`filterName`、`contextPath`、`type`、`rollbackSupported`（这些字段允许差异 / 不属于安全闸门核心）。

#### 2.1.2 `agent/src/main/java/com/memhunter/agent/cleaner/PlanStaleException.java`

```java
public class PlanStaleException extends RuntimeException {
    public PlanStaleException(String message) { super(message); }
}
```

异常消息格式（约束）：

```
plan stale: <field> mismatch (persisted=<X>, fresh=<Y>[, confirmFlag=<Z>])
```

forced 字段的消息额外带 `confirmFlag` 三元组。

### 2.2 修改

#### 2.2.1 `agent/.../cleaner/TomcatFilterCleaner.java`

`releaseOriginalFilterConfig`（Phase D 内部方法）改返回 `String` 描述：

```java
private String releaseOriginalFilterConfig() {
    Object config = currentBackup.originalFilterConfig;
    if (config == null) return "phase-D: no-release-method";
    try {
        Method m = config.getClass().getMethod("release");
        m.invoke(config);
        return "phase-D: destroy-ran";
    } catch (NoSuchMethodException nsme) {
        return "phase-D: no-release-method";
    } catch (InvocationTargetException ite) {
        Throwable cause = ite.getCause() != null ? ite.getCause() : ite;
        return phaseDThrew(cause);
    } catch (Throwable t) {
        return phaseDThrew(t);
    }
}

private static String phaseDThrew(Throwable t) {
    String msg = t.getMessage() == null ? "" : t.getMessage();
    return "phase-D: destroy-threw: " + t.getClass().getSimpleName() + ": " + msg;
}
```

`execute()` 内 `executedSteps.add(...)` 改用方法返回值，不再硬编码字符串。

#### 2.2.2 `agent/.../MemHunterAgent.java`

`dispatchNonScan` 的 `clean --confirm` 分支按下方数据流改造（详见 §3）：

- 读持久化 plan
- 调 `cleaner.plan(finding, confirmForceFlag)` 拿 fresh plan
- 调 `PlanReconciler.requireConsistent(persisted, fresh, confirmForceFlag)`
- catch `PlanStaleException` → 写 `CleanResult{success=false, ...}` + 返回 `EXIT_PLAN_STALE`
- 一致 → 进入既有 v0.6 `cleaner.execute(fresh, confirmForceFlag)` 路径

新增退出码常量：`EXIT_PLAN_STALE = 3`（与 1=usage、2=internal 区分）。

## 3. 数据流

### 3.1 `clean --confirm` 完整路径（修改后）

```text
用户执行：
   memshell-attach.jar <pid> agent.jar clean --id <fid> --confirm [--force]
                                  │
                                  ▼
   AttachMain：
     ① 读 evidence/<fid>/clean-plan.json （prompt 摘要用）
     ② CleanInteractor.promptYes() 读 stdin
     ③ 用户输入 "yes" → loadAgent(...)
                                  │
                                  ▼
   agentmain → MemHunterAgent.dispatchNonScan("clean", args)
                                  │
                                  ▼
   ┌────────────────────────────────────────────────────────────┐
   │ clean --confirm 分支                                       │
   │                                                             │
   │  1. persisted = CleanPlanReader.read(planFile)             │
   │  2. finding = locateByIdFromFreshScan(persisted.findingId) │
   │  3. confirmForceFlag = args.options.containsKey("force")   │
   │  4. fresh = cleaner.plan(finding, confirmForceFlag)        │
   │                                                             │
   │  ┌─ 新增 v0.6.1 ─────────────────────────────────────────┐ │
   │  │ try {                                                  │ │
   │  │   PlanReconciler.requireConsistent(                   │ │
   │  │       persisted, fresh, confirmForceFlag);            │ │
   │  │ } catch (PlanStaleException e) {                      │ │
   │  │   writeFailureResult(fid, e.getMessage());            │ │
   │  │   return EXIT_PLAN_STALE;                             │ │
   │  │ }                                                      │ │
   │  └────────────────────────────────────────────────────────┘ │
   │                                                             │
   │  5. result = cleaner.execute(fresh, confirmForceFlag)      │
   │  6. EvidenceWriter.writeResult(fid, result)                │
   └────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
   attach 端读 evidence/<fid>/clean-result.json，打印摘要
```

### 3.2 关键不变性

- **mutation 永不发生在 Reconciler 之前**：dispatch 顺序保证 `PlanReconciler` 在 `cleaner.execute()` 之前；stale 失败时运行时绝不被改。
- **fresh plan 完整生成才比对**：`cleaner.plan()` 已经做了 Phase A（type/score 校验）+ Phase B（构造 backup）；如果 fresh plan 本身是 null（finding 消失/score 不达标/类型不对），走既有 v0.6 失败路径，不进入 PlanReconciler。
- **forced 三方校验**：`persisted.forced ≡ fresh.forced ≡ confirmForceFlag`，三者全等才放行。任两个不等即 stale。
- **Plan A（dry-run）路径不受影响**：dry-run 不读持久化 plan，只生成并落盘，PlanReconciler 不在 dry-run 路径上。
- **退出码**：`EXIT_PLAN_STALE=3`。attach 端无需特别处理，正常打印 clean-result.json 的 failureReason 即可。

### 3.3 Phase D 标签数据流（独立）

```text
TomcatFilterCleaner.execute() 内：
   Phase C 完成 → executedSteps += "phase-C: ..."
   ↓
   String dStep = releaseOriginalFilterConfig();   ← 新签名，返回 String
      ├ release() 调用成功            → "phase-D: destroy-ran"
      ├ NoSuchMethodException         → "phase-D: no-release-method"
      └ 其他 Throwable                → "phase-D: destroy-threw: <Class>: <msg>"
   executedSteps.add(dStep);
   ↓
   Phase E（不变）
```

## 4. 错误处理

### 4.1 PlanStaleException 落盘路径

```java
CleanResult result = new CleanResult();
result.findingId = persisted.findingId;
result.success = false;
result.rolledBack = false;            // 没动运行时
result.verifiedDisappeared = false;
result.executedSteps = Arrays.asList(
    "pre-execute: plan staleness check FAILED — refusing to clean"
);
result.failureReason = e.getMessage();
result.executedAt = System.currentTimeMillis();
EvidenceWriter.writeResult(persisted.findingId, result);
return EXIT_PLAN_STALE;
```

### 4.2 异常分层

| 异常 | 来源 | dispatch 层动作 |
|---|---|---|
| `PlanStaleException` | PlanReconciler | 写 failure CleanResult + 退出 `EXIT_PLAN_STALE` |
| `CleanExecutionException` | doPhaseC | 既有 v0.6 路径（writeResult, return non-zero） |
| `RollbackFailedException` | RollbackManager | 既有 v0.6 路径 |
| `IOException`（plan 文件读不到） | CleanPlanReader.read() | 既有 v0.6 路径（提示先 dry-run） |

PlanReconciler 内部 **不** catch 任何东西 —— 单纯抛 PlanStaleException 让 dispatch 层处理。

### 4.3 Fail-fast 而非聚合差异的理由

- v0.6.1 是审计闸门，不是诊断工具；出现 stale 说明用户操作流程被破坏，第一个差异已足够定位。
- 简单 = 不可被规避；聚合消息容易被未来代码"修一半字段"的 bug 引入误判。

### 4.4 Phase D 异常处理（已敲定）

`releaseOriginalFilterConfig()` 内部 catch 分两类：

- `NoSuchMethodException` → `"phase-D: no-release-method"`
- `InvocationTargetException` → 解包 cause → `"phase-D: destroy-threw: <Class>: <msg>"`
- 其他 `Throwable` → 同上格式

所有 Throwable 都被吞 —— Phase D 永远不触发 rollback（v0.6 设计 §5 既定原则）。

## 8. 风险与限制

| 风险 | 缓解 |
|---|---|
| 用户保留旧 plan 文件后用新 finding（不同 className）confirm | findingId/className 比对兜底，必失败 |
| 用户手工编辑 plan 文件改字段 | 同样会被三方校验抓到 |
| Phase D 异常类名为内部类（`A$B`）的可读性 | `getSimpleName()` 仍可输出，操作员可结合 stacktrace 复核 |
| dry-run 与 confirm 之间运行时被攻击者重新注入相似 filter | finding id 由 type+className+filterName 决定；同名同类 filter 仍是同一 finding，fresh plan 仍会被生成 → 由复扫 Phase E 兜底 |
