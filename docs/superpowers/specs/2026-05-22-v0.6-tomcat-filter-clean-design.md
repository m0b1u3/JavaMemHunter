## 1. 目标与非目标

### 1.1 目标

1. 提供 `clean --id <findingId>` 命令，按 Finding ID 精准清理 Tomcat Filter 型内存马。
2. 提供 `verify --id <findingId>` 命令，复扫确认目标 Finding 是否消失。
3. 清理流程强制 `--dry-run` → 人工审阅 → `--confirm` + 终端 `yes` 二次确认两阶段。
4. 清理前导出完整证据包（finding.json / clean-plan.json / before-snapshot.json / bytecode.bin）。
5. 清理操作使用 **原子性副本替换** 策略（§21.1），最小化并发窗口。
6. 失败时通过 RollbackManager 自动恢复 filterDef/filterMap/filterConfig 快照。
7. 闸门：默认仅清理 `score ≥ 7`（high/critical），可通过 `--force` 跳过但仍需 `--confirm`，报告标记 `forced=true`。

### 1.2 非目标

1. **不**清理 Tomcat Servlet / Listener / Valve（v0.6.1）。
2. **不**清理 Spring Mapping / Interceptor / Bean（v0.6.2 / v0.7）。
3. **不**提供 `clean-all` 批量清理（设计文档 §20.3 明确禁止）。
4. **不**在清理时主动等待请求排空（§21.1）。
5. **不**支持 agent 卸载（JVM 限制，§21.2）。

## 2. 整体流程

```text
[1] 用户先 scan                                 ./memshell-agent.jar scan --output report.json
                                                       │
[2] 用户从 report.json 中选定 finding-filter-xxx        ▼
                                                ./memshell-attach.jar <pid> agent.jar clean --id finding-filter-xxx --dry-run
                                                       │
                                                       ▼
                                                attach 端 loadAgent(dry-run)
                                                       │
                                                agent 内：
                                                  - 复扫定位目标 Finding
                                                  - 校验 type=tomcat-filter
                                                  - 校验 score ≥ 7（或 --force）
                                                  - 生成 CleanPlan + EvidenceBundle 落盘
                                                  - 不修改任何运行时对象
                                                       │
                                                attach 端打印 CleanPlan 摘要
                                                       │
[3] 用户再次执行：                                       ▼
                                                ./memshell-attach.jar <pid> agent.jar clean --id finding-filter-xxx --confirm
                                                       │
                                                attach 端：
                                                  - 读取上一次 dry-run 生成的 CleanPlan
                                                  - 打印完整计划 + 风险提示
                                                  - 提示 "Type yes to confirm:"
                                                  - 从 stdin 读取一行，必须严格等于 "yes"
                                                       │
                                                       ▼
                                                attach 端 loadAgent(confirm)
                                                       │
                                                agent 内 TomcatFilterCleaner：
                                                  - 再次复扫确认目标仍存在
                                                  - backup filterDef / filterMap / filterConfig
                                                  - 构造新副本（移除目标）
                                                  - 反射一次性 set 回 standardContext
                                                  - 调用 filter.destroy()
                                                  - 复扫 verify
                                                       │
                                                  失败 → RollbackManager 恢复快照
                                                       │
                                                       ▼
                                                写出 clean-result.json

[4] （可选）用户单独复扫：
                                                ./memshell-attach.jar <pid> agent.jar verify --id finding-filter-xxx
```

## 3. 数据模型

### 3.1 CleanPlan

```java
public class CleanPlan {
    public String findingId;            // 来自 scan 报告
    public String type;                 // 固定 "tomcat-filter"
    public String filterName;
    public String filterClass;
    public List<String> urlPatterns;
    public String contextPath;
    public int score;
    public String level;
    public boolean forced;              // --force 是否启用
    public List<String> steps;          // 文本步骤，给人审
    public boolean rollbackSupported;   // v0.6 固定 true
    public String evidenceDir;          // evidence/finding-xxx/
    public String planFile;             // evidence/finding-xxx/clean-plan.json
    public long generatedAt;
}
```

### 3.2 CleanResult

```java
public class CleanResult {
    public String findingId;
    public boolean success;
    public boolean rolledBack;
    public List<String> executedSteps;
    public String failureReason;        // null on success
    public boolean verifiedDisappeared; // 复扫后目标是否消失
    public long executedAt;
}
```

### 3.3 EvidenceBundle 目录结构

```text
<output-dir>/evidence/finding-filter-a3f92c1d/
├── finding.json            # 原 Finding 完整字段
├── clean-plan.json         # CleanPlan
├── before-snapshot.json    # filterDef/filterMap/filterConfig 反射读出的快照
├── bytecode.bin            # Filter 类字节码（来自 v0.4 ClassBytecodeReader）
├── bytecode.sha256
└── clean-result.json       # confirm 阶段写出
```

### 3.4 FilterBackup（内部回滚用，不落盘）

```java
class FilterBackup {
    Object originalFilterDef;          // 原 FilterDef 对象引用
    List<Object> originalFilterMaps;   // 原 FilterMap 列表副本
    Object originalFilterConfig;       // 原 ApplicationFilterConfig
    Map<String, Object> originalFilterConfigsMap;  // 整个 filterConfigs Map 的浅拷贝
}
```

## 4. CLI 设计

### 4.1 新增命令

| 命令 | 说明 |
|---|---|
| `clean --id <id> --dry-run [--output <dir>] [--force]` | 生成 CleanPlan + EvidenceBundle，不修改运行时 |
| `clean --id <id> --confirm [--force]` | 读取上次 dry-run 结果，提示 yes，执行清理 |
| `verify --id <id>` | 复扫并对比 Finding ID 是否消失，输出 verify-result.json |

### 4.2 AgentArgs 扩展

`KNOWN_OPTIONS` 追加：`id` / `dry-run` / `confirm` / `force` / `evidence-dir`

支持的 command 由 `scan` 扩展到 `scan` / `clean` / `verify`。

### 4.3 互斥校验

- `--dry-run` 与 `--confirm` 必须二选一，缺一时报错 `clean requires either --dry-run or --confirm`
- `--force` 必须与 `--confirm` 同时使用（dry-run 不影响数据，无需 force；force 不能裸用以防误操作）
- `--id` 必填

### 4.4 attach 端交互（§15.2.1）

`--confirm` 阶段流程（伪代码）：

```text
1. attach 端读取本地 evidence/finding-xxx/clean-plan.json
   - 若不存在 → 提示 "run --dry-run first"，退出
2. 打印 CleanPlan 摘要（filterName / urlPatterns / score / steps / forced）
3. 打印 "Type \"yes\" to confirm (anything else cancels):"
4. BufferedReader.readLine() 从 System.in 读一行
5. 若不严格等于 "yes" → 打印 "Cancelled."，退出 code 1
6. loadAgent(agent.jar, "clean --id xxx --confirm [--force]")
7. 等待 agent 写出 clean-result.json，打印结果摘要
```

## 5. TomcatFilterCleaner 实现

### 5.1 字段访问

需要反射访问 `StandardContext` 的 3 个 Map/数组：

| 字段 | 类型 | 用途 |
|---|---|---|
| `filterDefs` | `HashMap<String, FilterDef>` | filterName → FilterDef |
| `filterMaps` | `StandardContext$ContextFilterMaps`（内部包装类，含 `FilterMap[] array`） | URL pattern 映射数组 |
| `filterConfigs` | `HashMap<String, ApplicationFilterConfig>` | filterName → 已初始化的 FilterConfig |

`filterMaps` 字段细节：Tomcat 8/9/10 在 `StandardContext` 中是 `private final ContextFilterMaps filterMaps = new ContextFilterMaps()`，内部持有 `FilterMap[] array`。我们用反射访问 `array` 字段。

### 5.2 原子性副本替换流程

```text
[Phase A: 复扫与校验]
  1. invoke TomcatFilterScanner once
  2. 在结果中查找 finding.id == targetId
  3. 若未找到 → CleanResult{success=false, failureReason="finding no longer exists"}
  4. 若 score < 7 且未 --force → 失败 "score below threshold, use --force"

[Phase B: 备份（构造 FilterBackup）]
  5. 反射读 filterDefs → 备份目标 FilterDef
  6. 反射读 filterMaps.array → 备份匹配 filterName 的所有 FilterMap
  7. 反射读 filterConfigs → 备份目标 ApplicationFilterConfig
  8. 浅拷贝整个 filterConfigs Map（用于 catastrophic rollback）

[Phase C: 原子替换 — 顺序很关键]
  9. 新 filterConfigs：copy → remove(targetName) → reflectively set field
  10. 新 filterMaps.array：filter out target → reflectively set field
  11. 新 filterDefs：copy → remove(targetName) → reflectively set field

  顺序原因：先断 filterConfigs 入口，请求链上正在执行的 filter 不受影响
  （filterConfigs 是 ApplicationFilterChain 创建时查表的入口），
  然后才动 filterMaps 防止新请求命中，最后清 filterDefs。

[Phase D: 销毁实例]
  12. 调用 backup.originalFilterConfig.release()（含 filter.destroy()）
      包裹 try-catch，destroy() 异常不触发 rollback

[Phase E: 复扫验证]
  13. invoke TomcatFilterScanner again
  14. 若仍找到 targetId → CleanResult{success=false, verifiedDisappeared=false}
                          + 自动 rollback
  15. 否则 CleanResult{success=true, verifiedDisappeared=true}

[Phase F: 异常处理]
  16. Phase C 任一步抛异常 → RollbackManager.restore(backup)
      按相反顺序 set 回 filterDefs / filterMaps / filterConfigs
```

### 5.3 RollbackManager

```java
public class RollbackManager {
    public void restore(Object standardContext, FilterBackup backup) {
        // 按 Phase C 的反向顺序回写
        // 任一回写失败 → 抛 RollbackFailedException，attach 端建议重启服务
    }
}
```

## 6. 复扫验证（verify）

`verify` 命令复用 `TomcatFilterScanner`：

1. 全量扫描 Tomcat Filter
2. 在结果中查找 `finding.id == targetId`
3. 输出 `verify-result.json`：

```json
{
  "findingId": "finding-filter-a3f92c1d",
  "stillPresent": false,
  "verifiedAt": 1716345600000
}
```

clean --confirm 阶段在 Phase E 内部已经调用，verify 命令是给用户事后独立复核的入口。

## 7. 安全闸门

| 校验项 | clean dry-run | clean confirm |
|---|---|---|
| `--id` 必填 | ✓ | ✓ |
| Finding 必须存在 | ✓ | ✓（再次复扫） |
| type 必须为 `tomcat-filter` | ✓ | ✓ |
| `score ≥ 7` | ✓（除非 --force） | ✓（除非 --force） |
| `--confirm` 需配 attach 端 yes | — | ✓ |
| `--force` 必须配 `--confirm` | — | ✓ |
| EvidenceBundle 必须成功写出 | ✓ | ✓ |

`--force` 在 CleanPlan / CleanResult 中固定标记 `forced=true`，供事后审计。

## 8. 风险与限制

| 风险 | 缓解 |
|---|---|
| `filterMaps.array` 字段名在 Tomcat 7 与 8+ 不同（数组 vs ContextFilterMaps 包装） | 适配两种结构；不支持的版本提前失败并提示重启 |
| filter.destroy() 自身抛异常 | catch 但不 rollback（filter 实例已从注册表移除，destroy 失败不影响入口断开） |
| 清理过程中正在执行的 filter chain | 副本替换最小化窗口；仍可能有 in-flight 请求继续走旧 filter 直到结束，文档明示 |
| `--force` 滥用清理正常 Filter | 报告强标记 forced=true；evidence 包永久保留 |
| Spring Boot 内嵌 Tomcat 同一字段名 | TomcatEmbeddedContext 继承 StandardContext，字段一致，v0.5 已验证 |
| 多次 attach 类残留 | 沿用 §21.2 README 提示 |

## 9. 测试方案

### 9.1 单元测试

| 测试类 | 覆盖 |
|---|---|
| `CleanPlanTest` | 序列化 / 反序列化 round-trip |
| `AgentArgsCleanTest` | clean / verify 命令解析，互斥校验 |
| `RollbackManagerTest` | 给定 backup 能恢复 filterDefs/filterMaps/filterConfigs |
| `TomcatFilterCleanerTest` | mock StandardContext，验证 Phase C 字段写入顺序 |

### 9.2 端到端验证（test-target-injector）

```text
1. 启动 test-target（含 FakeFilterInjector）
2. memhunter scan --output before.json
   → 期望：finding-filter-xxx，score ≥ 25
3. memhunter clean --id finding-filter-xxx --dry-run --output ./evidence
   → 期望：evidence/finding-filter-xxx/{finding.json, clean-plan.json, before-snapshot.json, bytecode.bin}
4. memhunter clean --id finding-filter-xxx --confirm
   → 输入 "no" → Cancelled，无任何修改
   → 输入 "yes" → 执行清理，clean-result.json {success: true, verifiedDisappeared: true}
5. memhunter scan --output after.json
   → 期望：FakeFilter 已消失
6. 触发任意 HTTP 请求 → 期望返回正常（FakeFilter 已被移除）
```

### 9.3 失败路径测试

- finding 不存在 → 友好报错
- score=5 且未 --force → 拒绝清理
- score=5 + --force + --confirm → 允许，CleanResult.forced=true
- 模拟 Phase C 失败 → 验证 rollback 成功
- 模拟 verify 失败 → 验证自动 rollback
