# v0.13 设计：伪装框架包内存马检测增强

**日期**：2026-06-04
**前置版本**：v0.12.1（误报治理 + webapp loader 注入）
**背景**：v0.12.1 发布后，实地复扫一台注入了**哥斯拉（Godzilla）内存马**的 Tomcat 9.0.94，
发现工具**检出了全部 5 个哥斯拉马**（3 个 Filter + 2 个 Servlet），但判级偏低——
都停在 high/suspicious，没到 critical。根因是哥斯拉把 Jackson 库的类伪装成
`org.apache.coyote.*` 包名，**滥用扫描器的受信包白名单**，命中 `whitelist-hit -5` 把告警压低。

---

## 1. 目标 & 非目标

### 1.1 目标

让「伪装成受信框架包 + 动态生成无 jar 来源」的内存马（哥斯拉为典型）从 high/suspicious
升到 critical，且**零误报**——不误伤任何合法框架类。

### 1.2 非目标

- 不做反序列化型字节码特征检测（readObject / Jackson 调用链 / defineClass 锚点）——FP 风险高，留待后续评估
- 不改 scanner、不读字节码——纯评分层改动
- 不改 clean/verify 流程

---

## 2. 核心洞察

真框架类与哥斯拉伪装类的决定性差异在 **codeSource**：

| | 真 `org.apache.coyote.Foo` | 哥斯拉伪装 `org.apache.coyote.TypeIdResolverBase` |
|---|---|---|
| 来源 | 从 `lib/tomcat-coyote.jar` 加载 | 动态 `defineClass` 生成 |
| codeSource | 非空（指向 jar） | **null** |

**「白名单前缀命中」与「codeSource=null」同时出现是自相矛盾的** —— 真框架类不可能没有
codeSource。这个矛盾就是伪装的铁证。

### 2.1 真实评分证据

哥斯拉核心 Filter（`org.apache.coyote.jsontype.impl.TypeIdResolverBase`，urlPattern `/*`）
v0.12.1 的实际评分：

```
implements-web-component +3
code-source-null         +3
runtime-only             +1
url-pattern-wildcard     +2
high-entropy-class-name  +1
unusual-classloader      +2
whitelist-hit            -5   ← 伪装滥用白名单，致命的一刀
────────────────────────────
合计 = 7 (high)   本该 critical
```

最单薄的伪装类（`class-filter` 型，无 `/*`、无 runtime-only）：

```
implements-web-component +3
code-source-null         +3
unusual-classloader      +2
whitelist-hit            -5
────────────────────────────
合计 = 3 (low)
```

## 3. 架构：两处改动（职责分离）

### 3.1 改 `WhitelistHitRule` —— 白名单可信度门

减分前加可信度校验：**仅当 finding 的 codeSource 非空时才减 -5**；codeSource 为 null 或空串
则返回 0（不减分）。职责单一：只管「该不该信任白名单命中」。

```java
public int evaluate(Finding finding, ScanContext ctx) {
    if (finding == null || ctx == null || ctx.whitelist == null) return 0;
    if (!ctx.whitelist.isFrameworkPackage(finding.className)) return 0;
    // v0.13: 真框架类一定有 jar 来源；codeSource 为空说明是动态生成的伪装类，不予信任
    if (finding.codeSource == null || finding.codeSource.isEmpty()) return 0;
    return -5;
}
```

受信前缀判定沿用现有 `ctx.whitelist.isFrameworkPackage(className)`（`Whitelist` 已公开此方法，
`MappingPathDisguiseRule` / `NonBusinessPackageRule` 也都用它）。改动只是在原 `-5` 前加 codeSource 门。

### 3.2 新增 `MasqueradedPackageRule` —— 伪装检测加分

className 命中受信白名单前缀**且** codeSource 为空 → +5（伪装铁证）。职责单一：只管
「是否冒充框架类」。

```java
public class MasqueradedPackageRule implements ScoringRule {
    public String name() { return "masqueraded-package"; }

    public int evaluate(Finding finding, ScanContext ctx) {
        if (finding == null || ctx == null || ctx.whitelist == null) return 0;
        if (!ctx.whitelist.isFrameworkPackage(finding.className)) return 0;
        if (finding.codeSource == null || finding.codeSource.isEmpty()) return 5;
        return 0;
    }
}
```

两条规则用**同一个判定** `ctx.whitelist.isFrameworkPackage`，逻辑互斥：同一 finding 要么
「可信（codeSource 非空）→ WhitelistHitRule 减 5」，要么「伪装（codeSource 空）→
MasqueradedPackageRule 加 5」，绝不同时触发。

### 3.3 装配

`RuleEngine.defaultRules()` 加入 `new MasqueradedPackageRule()`（位置任意，分数求和）。

### 3.4 文件

- 修改：`agent/.../scoring/rules/WhitelistHitRule.java`
- 修改：`agent/.../scoring/rules/WhitelistHitRuleTest.java`
- 新增：`agent/.../scoring/rules/MasqueradedPackageRule.java`
- 新增：`agent/.../scoring/rules/MasqueradedPackageRuleTest.java`
- 修改：`agent/.../scoring/RuleEngine.java`（装配）
- 修改：`agent/.../scoring/RuleEngineTest.java`（集成测试）

`WhitelistHitRule` 与 `MasqueradedPackageRule` 均调用 `ctx.whitelist.isFrameworkPackage(className)`
（`Whitelist.isFrameworkPackage` 已是 public，受信前缀在 `DefaultWhitelist`）。不新建第二份名单。

## 4. 误报防护（保证零误报）

唯一风险：合法框架类碰巧 codeSource=null。逐项排除：

- 真 `org.apache.coyote.*` / `catalina.*` / `tomcat.*` / `juli.*` 类**总是**从 `lib/*.jar`
  加载，codeSource 必非空 → 不被 MasqueradedPackageRule 命中，照常享受 WhitelistHitRule 减分。
- bootstrap 加载的核心类 codeSource 为 null，但受信前缀里**没有** `java.*` / `javax.*`
  （那些是 JVM 核心，不在 Tomcat 白名单）→ 不受影响。
- 结论：「受信前缀类 + codeSource=null」在正常环境中不存在，只有伪装马会触发。**零误报。**

**agent-\* 保护**：两规则都是普通 ScoringRule，`RuleEngine.evaluateOne` 对 `agent-*` finding
早退、不跑规则链 → 不受影响，沿用 v0.10 起的现有防线。

## 5. 预期效果（套用真实评分）

| finding | v0.12.1 | v0.13（-(-5) + (+5) = +10） | 结果 |
|---|---|---|---|
| `TypeIdResolverBase` `/*` Filter | 7 (high) | 17 | **critical** |
| `JsonAppend` / `PropertyWriter` `/*` Filter | 6 (suspicious) | 16 | **critical** |
| 最单薄伪装 `class-filter` | 3 (low) | 13 | **critical** |
| `/dddd`、`/favicon.ico` Servlet（className=null，**非** coyote 前缀） | 8 (high) | 8 | high（不受本次改动影响——它们没有伪装包名，靠 className/codeSource=null 已正确判 high）|

注：`/dddd`、`/favicon.ico` 两个哥斯拉 Servlet 马的 className 为 null（不含受信前缀），
不触发本次两条规则，维持 high。本次聚焦伪装**包名**类马；className=null 型已被现有规则判 high，
不在 v0.13 范围（如需升 critical 可后续评估，但 high 已足以告警）。

## 6. 测试 & 验收

### 6.1 单元测试

**WhitelistHitRuleTest（改）：**
- 受信前缀 + codeSource 非空 → -5（原行为保留）
- 受信前缀 + codeSource=null → 0（新断言）
- 受信前缀 + codeSource 空串 → 0（新断言）
- 非受信前缀 → 0

**MasqueradedPackageRuleTest（新）：**
- `org.apache.coyote.X` + codeSource=null → +5
- `org.apache.coyote.X` + codeSource 非空 → 0
- 普通业务类 `com.example.Foo` + codeSource=null → 0
- className=null → 0

**RuleEngineTest（加集成）：**
- 哥斯拉式 finding（`org.apache.coyote.jsontype.impl.TypeIdResolverBase`, codeSource=null,
  type=tomcat-filter, urlPattern `/*`, isDynamic=true）走完整链 → level=critical
- 真框架类（同前缀 + codeSource 指向 jar）走链 → 仍享受白名单减分、不被伪装规则加分

### 6.2 验收（实地，哥斯拉 ground truth）

重启 Tomcat 9.0.94 + 注入哥斯拉内存马 → 复扫，验证：
- 3 个伪装包名 Filter 马（`TypeIdResolverBase` / `JsonAppend` / `PropertyWriter`）全部 **critical**
- 数量与哥斯拉客户端 `getAllFilter` 显示的一致
- 真阳不回退：冰蝎 agent-bytecode-tampered 仍 critical、JSP shell 仍 high
- 误报不回退：v0.12.1 的 Tomcat examples 抑制仍生效（仍 low）
