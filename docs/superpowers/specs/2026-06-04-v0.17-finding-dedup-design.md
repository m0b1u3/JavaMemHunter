# v0.17 设计：finding 同类去重/合并

**日期**：2026-06-04
**前置版本**：v0.16（JSP webshell 访问路径反推）
**背景**：同一个恶意类被多个 scanner 从不同视角各报一次——哥斯拉的
`org.apache.coyote.ser.PropertyWriter` 既被 TomcatFilterScanner 报为 `tomcat-filter`
（score 16、`path=[/*]`），又被 ClassScanner 报为 `class-filter`（score 13、无路径）。结果 critical
列表里同一个类出现两次，使用人员迷惑（"是两个马吗？"）。需合并同类 finding。

---

## 1. 目标 & 非目标

### 1.1 目标

按 className 合并同类 finding：同一 className 的多条只保留信息最全的一条，消除重复。

### 1.2 非目标

- 不跨 className 合并（不同类名即使疑似同一攻击也不合）
- 不改 scanner、不改评分逻辑、不碰 clean/verify
- className 为 null 的 finding 不参与合并（无法判同一性，保持独立）

---

## 2. 核心规则

- 按 `className` 分组（className==null 的不分组，原样保留）
- 每组选一条「主条」：
  1. **score 最高**那条
  2. score 并列 → 取 **attributes 含路径字段**（urlPatterns/mappings/jspPath/pattern/includePatterns/
     injectedStrings 任一非空）的那条
  3. 仍并列 → 取原列表中靠前的（稳定排序，不随机）
- 组内其余条丢弃
- 效果：容器视角（tomcat-/spring-，分更高、有路径）自然胜出，class-* 冗余条被丢；
  class-* 唯一发现（容器没报，如 JSP shell、哥斯拉工具类）→ 该组仅一条 → 保留

---

## 3. 架构

agent 端，出报告前合并。

### 3.1 新增 `FindingDeduplicator`（纯函数）

`agent/src/main/java/com/memhunter/agent/FindingDeduplicator.java`：
```java
public final class FindingDeduplicator {
    private FindingDeduplicator() {}

    private static final String[] PATH_KEYS = {
        "urlPatterns", "mappings", "jspPath", "pattern", "includePatterns", "injectedStrings"
    };

    /**
     * Merges findings that refer to the same class. Findings with a null className are not merged
     * (identity cannot be established) and are kept as-is. For each group sharing a className, the
     * "richest" finding is kept: highest score, then (on tie) the one carrying an access-path
     * attribute, then (still tied) the earliest in the input order. All other findings in the group
     * are dropped. Input order of survivors is preserved.
     */
    public static List<Finding> dedupe(List<Finding> all) {
        if (all == null) return new ArrayList<>();
        // group by className (LinkedHashMap preserves first-seen order); null className -> kept aside
        Map<String, Finding> best = new LinkedHashMap<>();
        List<Finding> nullClass = new ArrayList<>();
        List<Finding> result = new ArrayList<>();   // placeholder slots for ordering

        // First pass: pick the best per className.
        for (Finding f : all) {
            if (f == null) continue;
            if (f.className == null) { nullClass.add(f); continue; }
            Finding cur = best.get(f.className);
            if (cur == null || isRicher(f, cur)) {
                best.put(f.className, f);
            }
        }
        // Emit in first-seen order of className, interleaving null-class findings is not required;
        // simplest stable output: best-per-class in className first-seen order, then null-class ones.
        result.addAll(best.values());
        result.addAll(nullClass);
        return result;
    }

    /** True if candidate should replace current as the kept finding. */
    private static boolean isRicher(Finding candidate, Finding current) {
        if (candidate.score != current.score) return candidate.score > current.score;
        boolean candPath = hasPath(candidate);
        boolean curPath = hasPath(current);
        if (candPath != curPath) return candPath;     // tie on score -> prefer one with a path
        return false;                                  // fully tied -> keep current (earlier wins)
    }

    private static boolean hasPath(Finding f) {
        if (f.attributes == null) return false;
        for (String k : PATH_KEYS) {
            Object v = f.attributes.get(k);
            if (v == null) continue;
            if (v instanceof java.util.Collection) {
                if (!((java.util.Collection<?>) v).isEmpty()) return true;
            } else if (!String.valueOf(v).isEmpty()) {
                return true;
            }
        }
        return false;
    }
}
```

注：`best` 用 LinkedHashMap，键首次出现顺序即输出顺序——稳定。第一次见到某 className 时该条入 map，
后续更优条替换 value 但**不改键顺序**，所以输出顺序按 className 首次出现位置，符合"稳定"。

### 3.2 调用点（MemHunterAgent）

在 `new RuleEngine().evaluate(all, ...)` 之后、`report.findings = all;` 之前插入：
```java
            all = FindingDeduplicator.dedupe(all);
```
这样 `report.findings`、`populateSummary`、JSON、终端摘要全基于去重后列表，三者一致。

**为什么在评分后**：选主条按 score，必须先评分。

## 4. 测试 & 验收

### 4.1 单元测试（FindingDeduplicatorTest）

构造 Finding（直接 new、设 type/className/score/attributes）：
- 同 className：tomcat-filter(score 16) + class-filter(score 13) → 结果只 1 条，是 score 16 那条
- 同 className 同 score：一条有 urlPatterns、一条无 → 保留有路径那条
- 同 className 同 score 都无路径 → 保留原列表靠前那条（稳定）
- className=null 多条 → 全保留，不合并
- 不同 className 各一条 → 全保留
- 空列表 / null 输入 → 返回空列表
- 输出顺序：按 className 首次出现顺序 + 末尾接 null-class 条

### 4.2 验收（实地）

对哥斯拉靶机 scan（含 coyote 伪装类的 class-* + tomcat-* 重复），验证：
- 同 className 的 `org.apache.coyote.*` 只出现一条（tomcat-filter 那条，带 path=[/*]），
  class-filter/class-servlet 冗余条消失
- summary 的 critical 计数随之下降、与终端列出条数一致
- 真阳不丢：JSP shell（className 唯一）、哥斯拉 Servlet 马（className=null）仍各自保留

## 5. 参考

- 重复来源：ClassScanner（`class-<type>`，扫所有已加载类）vs TomcatFilterScanner/
  TomcatServletScanner/SpringMappingScanner 等（容器视角，有路径、分更高）对同一类各报一次
- finding id 含 type（`FindingIdGenerator.generate(type, className, disc)`），故 class-filter 与
  tomcat-filter 的同名类 id 不同、不会被 id 天然去重——必须按 className 合并
- Finding 字段：`type`、`score`(int)、`className`、`attributes`(Map，默认非 null)
- 调用点：MemHunterAgent scan 流程，RuleEngine.evaluate 之后、report.findings 赋值之前
- clean 按 finding id 定位（FindingLocator 复扫匹配 id）——去重保留主条，主条 id 仍有效；被丢弃的
  冗余条本就是同一个类的另一视角，clean 主条即清除该类
