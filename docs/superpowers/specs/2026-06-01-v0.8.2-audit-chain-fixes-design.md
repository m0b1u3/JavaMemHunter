## 1. 目标与范围

### 1.1 目标

修补 v0.8.1 E2E 中发现的三个 audit-chain / verify 漏洞，恢复"清理 → 验证"反馈环的可信度。

**3 个 issue：**

1. **VerifyExecutor 只扫 Filter（最严重）**：v0.6 引入的 `VerifyExecutor.stillPresent` 只跑 `TomcatFilterScanner`。v0.7 加了 Servlet/Listener/Valve cleaner、v0.8 加了 Spring Mapping/Interceptor cleaner，但 VerifyExecutor 未同步升级。后果：**对除 Filter 外的 5 种 finding type，verify 命令永远返回 stillPresent=false（假阴性）**，让操作员误判清理成功。
2. **Force-gate 阻断 dry-run**：`AgentArgs.validate` 第 73 行 `hasForce && !hasConfirm → IllegalArgumentException("--force must be used with --confirm")` 阻断 `clean --dry-run --force` 路径。后果：**sub-threshold finding（score < 7）无法生成 evidence bundle**，无法走完整的 dry-run → 人工审阅 → confirm 流程。
3. **Plan-missing 不友好崩栈**：`clean --confirm` 时若 plan 文件不存在，`AttachMain` 第 50 行 `CleanPlanReader.read` 抛 Jackson IOException 崩到 17 行 Java stack trace。

### 1.2 修复策略

- **Verify**：抽取 `MemHunterAgent.findFindingById` 到新类 `agent/.../FindingLocator.java`（public static），VerifyExecutor 接受 `(tomcatCtx, springCtx)` 双 context，调 FindingLocator 跑所有 6 类 scanner。
- **Force-gate**：删除 `AgentArgs.validate` 第 73-75 行。一致性由 v0.6.1 PlanReconciler 在 confirm 阶段保证（三方 forced 一致性）。
- **Plan-missing**：`AttachMain` line 50 之前加 `Files.exists` 检查，缺失时友好打印 `"[memhunter] plan file not found at <path>; run --dry-run first"` + 返回 EXIT_USAGE (2)。

### 1.3 非目标

- 不引入新 CLI 选项
- 不改 CleanPlan / CleanResult / VerifyResult schema（向后兼容旧 evidence）
- 不修复 v0.7 review 余下 stylistic nits
- 不重跑 v0.8.1 E2E（既有 evidence 文件保留，README 文档化"verify 巧合正确"语义；下次手动 E2E 时自然用新代码）

## 2. 组件改动

### 2.1 新增

#### 2.1.1 FindingLocator

`agent/src/main/java/com/memhunter/agent/FindingLocator.java`：

```java
package com.memhunter.agent;

import com.memhunter.agent.model.Finding;
import com.memhunter.agent.model.ScanContext;
import com.memhunter.agent.model.ScanReport;
import com.memhunter.agent.scanner.spring.SpringInterceptorScanner;
import com.memhunter.agent.scanner.spring.SpringMappingScanner;
import com.memhunter.agent.scanner.tomcat.TomcatFilterScanner;
import com.memhunter.agent.scanner.tomcat.TomcatListenerScanner;
import com.memhunter.agent.scanner.tomcat.TomcatServletScanner;
import com.memhunter.agent.scanner.tomcat.TomcatValveScanner;
import com.memhunter.agent.scoring.RuleEngine;
import com.memhunter.agent.scoring.Whitelist;
import com.memhunter.agent.scoring.baseline.BaselineIndex;

import java.util.ArrayList;
import java.util.List;

/**
 * Cross-scanner finding lookup. Runs all 4 Tomcat scanners (when tomcatCtx
 * is non-null) plus the 2 Spring scanners (when springCtx is non-null),
 * scores the merged result via RuleEngine, then matches by id.
 *
 * <p>Used by both clean dispatch and verify so that both code paths see the
 * same finding universe (the v0.8.1 root cause of false-negative verify was
 * a Filter-only scan in VerifyExecutor that disagreed with the clean path).
 */
public final class FindingLocator {

    private FindingLocator() {}

    public static Finding find(Object tomcatCtx, Object springCtx, String id) {
        if (id == null) return null;
        ScanReport report = new ScanReport();
        List<Finding> all = new ArrayList<>();
        if (tomcatCtx != null) {
            all.addAll(new TomcatFilterScanner(tomcatCtx).scan(report));
            all.addAll(new TomcatServletScanner(tomcatCtx).scan(report));
            all.addAll(new TomcatListenerScanner(tomcatCtx).scan(report));
            all.addAll(new TomcatValveScanner(tomcatCtx).scan(report));
        }
        if (springCtx != null) {
            all.addAll(new SpringMappingScanner(springCtx).scan(report));
            all.addAll(new SpringInterceptorScanner(springCtx).scan(report));
        }
        new RuleEngine().evaluate(all,
                new ScanContext(springCtx, Whitelist.defaults(), false, BaselineIndex.empty()));
        for (Finding f : all) {
            if (f != null && id.equals(f.id)) return f;
        }
        return null;
    }
}
```

设计要点：
- `tomcatCtx != null` 守卫允许单纯 Spring 上下文场景（与现有 `springCtx != null` 守卫对称）
- ScanContext 第一参数沿用 `MemHunterAgent.findFindingById` 既有约定（`springCtx`）
- 不带 baseline / whitelist 自定义（与既有 findFindingById 行为一致）

## 3. 数据流

### 3.1 Force-gate 修复后的合法 sub-threshold 清理

```text
score < 7 finding 的清理流程:

  scan → 看到 score=6 finding-spring-mapping-xxx
       │
       ▼
  clean --id xxx --dry-run --force --evidence-dir ./ev
       │
       ▼  AgentArgs.validate 不再拦截（第 73 行已删）
       │
  Agent: cleaner.plan(finding, forced=true)
       │  → CleanPlan{forced=true} 写入 evidence/xxx/clean-plan.json
       │  + before-snapshot.json + finding.json
       ▼
  人工审阅 evidence
       │
       ▼
  clean --id xxx --confirm --force --evidence-dir ./ev
       │
       ▼  AttachMain Files.exists(planFile) ✓
       ▼  CleanInteractor stdin yes ✓
       ▼
  Agent: persistedPlan = read(clean-plan.json)
         freshPlan     = cleaner.plan(finding, forced=true)
         PlanReconciler.requireConsistent(persisted, fresh, confirmForceFlag=true)
                       ↓
         persisted.forced (true) ≡ fresh.forced (true) ≡ confirmForceFlag (true) ✓
                       ↓
         cleaner.execute → CleanResult
       │
       ▼
  verify --id xxx → FindingLocator.find(tomcatCtx, springCtx, xxx)
                                       ↓
                  6 类 scanner 真实复扫 → 准确的 stillPresent
```

   │
   ▼

   │  tomcatCtx = locateTomcat(...)

## 4. 错误处理

### 4.1 VerifyExecutor 失败模式

| 输入 | 行为 |
|---|---|
| id 在所有 6 scanner 都找不到 | `stillPresent=false`（清理成功） |
| id 仍在某 scanner 结果中 | `stillPresent=true`（清理失败或重新注入） |
| tomcatCtx==null && springCtx==null | FindingLocator 返回 null → `stillPresent=false`（边界情况；与 v0.6 旧行为对齐——找不到即认为消失） |
| Scanner 内部异常 | Scanner 已 try-catch 转 `ScanReport.partialErrors`，返回空列表 → 同上 |

### 4.2 Force-gate 删除后的安全保证

删除"force 必须配 confirm"检查后**没有引入新的攻击面**：

| 场景 | 守门员 |
|---|---|
| dry-run --force 跑，confirm 不带 --force | PlanReconciler: persisted.forced=true ≠ confirmForceFlag=false → PlanStaleException → EXIT_PLAN_STALE |
| dry-run 不带 force，confirm 带 --force | PlanReconciler: persisted.forced=false ≠ confirmForceFlag=true → EXIT_PLAN_STALE |
| dry-run --force + confirm --force 一致 | 三方一致 → 通过（操作员意图明确） |
| `clean --id X --force` 单独（漏 dry-run/confirm） | AgentArgs.validate `clean requires either --dry-run or --confirm` 拒绝 |

`--force` 单独无意义（必有 --dry-run 或 --confirm，否则前面已拒绝）；配 --dry-run 时只写 plan 不动 runtime；配 --confirm 时由 PlanReconciler 严格闸门。**force-gate 删除是数据安全等价变换**。

### 4.3 Plan-missing 返回码

- AttachMain `return 2` —— 与 IllegalArgumentException 退出码语义一致（usage error）
- 不写 clean-result.json（与"未执行"语义一致）
- 不调 agent，节省 VirtualMachine.loadAgent 开销 + 不污染 PID 上的 attach 痕迹

### 4.4 既有错误处理不变

- PlanReconciler 三方一致性
- CleanExecutionException.didMutate
- RollbackFailedException 不可恢复
- Phase D 三标签

## 8. 风险与限制

| 风险 | 缓解 |
|---|---|
| Deprecated `VerifyExecutor(Object)` 单参构造可能被遗留代码继续用 | 不删，保留 binary compatibility；@Deprecated 标记提示 |
| 删除 force-gate 后，操作员可能"误打"导致意图不清 | PlanReconciler 三方一致性闸门兜底；force=true 在 plan/result JSON 中可见，审计可追溯 |
| FindingLocator 跑 6 scanner 性能开销 | clean/verify 是低频操作（人工触发），不在热路径；scan 已用同套 scanner 跑得很快 |
| AttachMain Files.exists 在权限不足时返回 false 但 plan 实际存在 | 抛 SecurityException 不被 Files.exists 包装；用户看到与 plan 不存在相同的错误信息，操作员根据 stderr 检查文件系统 |
| v0.8.1 已归档 evidence 里 5/6 verify-result 显示 stillPresent=false（巧合正确） | 不重跑；v0.8.2 文档说明 "v0.8.1 evidence under old VerifyExecutor; this is incidentally correct because findings were also absent from FilterScanner output, but 第 6 spring-mapping verify 是真实假阴性" |
