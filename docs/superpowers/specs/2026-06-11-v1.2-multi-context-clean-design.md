# v1.2 设计：多 context 清理修复 + 错误回传

**日期**：2026-06-11
**前置版本**：v1.1（JSP work 类误报抑制）
**背景**：实地测试 clean 功能时发现，clean/verify 在多 webapp 部署的 Tomcat 上必然
`finding not located` 失败，且该失败在 attach 终端被显示成 "loaded successfully"。

---

## 1. 根因

目标 Tomcat 9.0.94 部署了 5 个 webapp（docs / examples / host-manager / manager /
ROOT）。内存马（`tomcat-filter`，类名 `org.apache.jsp.demo.filter_005fmemshell_jsp$CmdFilter`，
`contextPath: ''` 即 ROOT，`urlPatterns:[/*]`）注册在 ROOT。

- **scan** 走 `TomcatScanner.scanContexts(tomcatContexts, report)`，遍历**全部** context →
  扫到马，report 中 id = `finding-tomcat-filter-06b56e08`。
- **clean / verify** 走 `MemHunterAgent.requireFirstContext(tomcatContexts)` →
  `firstContext` 只取 `tomcatContexts.get(0)`（部署顺序第一个，通常是 docs），再用
  `FindingLocator.find(ctx, springCtx, id)` 只在那一个 context 里重扫 → 找不到 ROOT 里的马 →
  `MemHunterAgent.java:159` 抛 `IllegalStateException: finding not located` → 被
  `agentmain` 最外层 catch（第 131 行）吞进目标进程 stderr。

`MemHunterAgent.dispatchNonScan` 的三条路径（verify 行 144、clean dry-run 行 153、
clean confirm 行 178）**全部**用 `requireFirstContext`，故多 webapp 下只要马不在第一个
context，clean/verify 三条路径全失效。CLI scan 不受影响。

**次生问题**：attach 端 `AttachExecutor` 只靠 `loadAgent` 是否抛 `AgentLoadException("0")`
判定成功，agent 内部异常对 attach 端完全不可见，故该 fatal error 被打印成
"loaded successfully" —— 掩盖了 bug。

---

## 2. 目标 & 非目标

### 2.1 目标
1. clean/verify 在多 webapp Tomcat 上能正确定位并清理任意 context 里的马。
2. clean/verify 的失败原因在 attach 终端可见（不再被吞）。

### 2.2 非目标
- 不改 scan（它已遍历全部 context，无 bug）。
- 不改 cleaner 的清理算法 / 回滚逻辑 / 证据格式。
- 不改 finding 数据结构（沿用 id 匹配，不引入 contextPath 定位）。
- 不支持含空格的 status-file / output 路径（沿用既有约束）。

---

## 3. 设计

### 3.1 多 context 定位（核心）

新增 `FindingLocator.findAcrossContexts`：

```java
public static final class Located {
    public final Finding finding;
    public final Object tomcatCtx;
    public final Object springCtx;
    public Located(Finding finding, Object tomcatCtx, Object springCtx) {
        this.finding = finding; this.tomcatCtx = tomcatCtx; this.springCtx = springCtx;
    }
}

/** 遍历所有 tomcat context，对每个算 springCtx 并调单 context find；命中即返回。全部未命中返回 null。 */
public static Located findAcrossContexts(List<?> tomcatContexts,
                                         java.util.function.Function<Object,Object> springCtxResolver,
                                         String id) {
    if (tomcatContexts == null || id == null) return null;
    for (Object tctx : tomcatContexts) {
        if (tctx == null) continue;
        Object sctx = springCtxResolver.apply(tctx);
        Finding f = find(tctx, sctx, id);
        if (f != null) return new Located(f, tctx, sctx);
    }
    return null;
}
```

- `springCtxResolver` 由 `MemHunterAgent` 传入（即现有 `locateApplicationContext`），保持
  FindingLocator 不依赖 MemHunterAgent 的私有方法。
- 复用现有单 context `find(tomcatCtx, springCtx, id)`，不改其逻辑。

`MemHunterAgent.dispatchNonScan` 三处改造（不再用 `requireFirstContext`）：

- **verify**（行 142–150）：
  ```java
  FindingLocator.Located loc = FindingLocator.findAcrossContexts(
          tomcatContexts, MemHunterAgent::locateApplicationContext, id);
  if (loc == null) throw new IllegalStateException("finding not located: " + id);
  VerifyExecutor.VerifyResult result =
      new VerifyExecutor(loc.tomcatCtx, loc.springCtx).verify(id, evidenceDir(args));
  ```
- **clean dry-run**（行 152–175）：
  ```java
  FindingLocator.Located loc = FindingLocator.findAcrossContexts(
          tomcatContexts, MemHunterAgent::locateApplicationContext, id);
  if (loc == null) throw new IllegalStateException("finding not located: " + id);
  Cleaner cleaner = CLEANER_REGISTRY.resolve(loc.finding.type, loc.tomcatCtx, loc.springCtx);
  // ... 其余不变，用 loc.finding / loc.tomcatCtx
  ```
- **clean confirm**（行 177–188）：`dispatchCleanConfirm` 改为接收 `List<?> tomcatContexts`，
  内部 `findAcrossContexts` 定位，用命中的 (tomcatCtx, springCtx) 走 reconcile + 执行。
  保留 `dispatchForTest(Object tomcatCtx, Object springCtx, AgentArgs)` 测试 seam：内部把
  单 ctx 包成单元素 list 调同一新路径，避免逻辑分叉。

`requireFirstContext` 这三处不再使用。

### 3.2 错误回传（让失败可见）

**通道**：状态文件，attach 端生成绝对路径经 agentArgs 传入。

1. **attach 端**（`AttachMain` / `AttachExecutor`）：对 clean/verify 命令，在
   `System.getProperty("java.io.tmpdir")` 下生成无空格绝对路径
   `memhunter-status-<pid>-<ts>.json`，作为 `--status-file <path>` 追加进 agentArgs。
   scan 命令不强制加（可选）。

2. **新增值类型** `OperationStatus`（在 agent 定义；attach 侧实现最小读取，不依赖 agent 模块）：
   字段 `boolean ok; String command; String id; String message; String error; String stacktrace;`

3. **agent 端**：`agentmain` 最外层包裹——
   - 解析出 `--status-file`（若有）。
   - try 成功路径结束时：写 `{ok:true, command, id, message}`。
   - catch 块：写 `{ok:false, command, id, error:t.getMessage(), stacktrace}` 后仍打印到
     stderr（保留现有行为）。
   - status-file 缺省 → 不写文件，只走原 stdout/stderr（向后兼容）。
   - 写 status-file 自身包 try/catch——写失败绝不能反过来让操作失败。

4. **attach 端**：`loadAgent` 返回后读 status-file——
   - 文件存在且 `ok:true` → 打印成功摘要，退出码 0。
   - `ok:false` → 打印 `[memhunter] operation FAILED: <error>`，非零退出码。
   - 文件不存在 / 解析失败 → 退回现有 "loaded successfully" 行为（不退化、向后兼容）。
   - 读完删除 status-file（清理临时文件）。

## 5. 测试 & 验收

### 5.1 单元测试（TDD）
- `FindingLocator.findAcrossContexts`：马在第 2 个 context → 命中；马在第 1 个 → 命中（不回归）；
  全未命中 → null；空列表 → null。
- `MemHunterAgentTest` dispatch：clean confirm，多 context 马在非首位 → 定位并执行。
- `OperationStatus` + Writer/Reader 往返：成功 ok:true；失败 ok:false+error；文件不存在 → reader 返回 null。
- attach 判定：ok:false → 非零退出码；ok:true → 0；文件缺失 → 退回 "loaded successfully"。

### 5.2 集成测试（CI）
- `integration-tests` 新增用例：部署 ≥2 个 context、马注入**非首个** context，
  跑 scan→clean→verify 全流程，断言清理成功。把本 bug 钉死在 CI。

### 5.3 实地验收（Tomcat 9.0.94，多 webapp，马在 ROOT）
- 重启 Tomcat + 重新注入马（agent 代码变更，必须重启目标 JVM）。
- scan → 拿 id → clean dry-run（出 plan/evidence）→ clean confirm（stdin yes）→ verify。
- 断言：dry-run 生成 evidence/plan；confirm 真删掉 filter；verify 报 stillPresent=false。
- 故意用不存在的 id 跑 clean → attach 终端直接显示 FAILED + 原因（验证错误回传）。
